# 大历史记录下的交互性能验证

新建/归档对话会触发 snapshot 刷新，设置返回和输入草稿会触发 App 渲染。排查确认有三处 renderer 重复工作：

- snapshot 合并对每条旧事件遍历新事件，复杂度为 O(previous × incoming)。改用 Map/Set 后保留新 snapshot 优先、原顺序及刷新期间到达的 notice，复杂度为 O(previous + incoming)。
- 链接确认 Provider 每次渲染创建新 Context value，绕过 Markdown 的 memo，让未变化的历史重复解析。现在 value 只随确认的 blocked 状态改变；回调和待确认目标仍使用最新值。
- 每次 App 渲染过滤全量事件，并在每轮再次扫描当前会话事件、分组。现在按事件数组缓存会话索引和轮次分组，同时索引子任务所属父轮次；设置、草稿变化复用结果。工具执行分组也按 events 引用缓存。

## 复现和结果

在仓库根运行：

```sh
node scripts/benchmark-history.mjs
pnpm exec vitest run apps/desktop/ui/history.test.ts apps/desktop/ui/history-app.test.tsx apps/desktop/ui/link-confirmation.test.tsx
```

云端 Node 24.19.0，25,000 条事件、500 轮，三次中位数：

| 测量 | 耗时 |
| --- | ---: |
| 原 snapshot 合并 | 1,251.7 ms |
| 修复后 snapshot 合并 | 7.6 ms |
| 修复后会话索引及轮次分组 | 8.8 ms |

时间受机器负载影响，测试用事件 ID 访问次数验证线性复杂度，不用毫秒阈值判定成功。

App 使用 25,000 条后台历史的内存 bridge fixture，验证新建、归档后恢复原会话，以及设置往返和输入草稿不再次调用 Markdown 解析器。Context 对照复测中，原实现首次解析加十次父更新共解析 11 次，修复后仅 1 次；回归验证十次父更新复用已解析 Markdown，同时确认仍调用最新 onOpen；现有用例覆盖流式文本变更取消旧链接、Escape、焦点恢复和单次确认。延迟 snapshot 回归验证 changed 连续到达时拒绝旧响应，并保留刷新期间送达的流式事件。

## 验证边界

以上基准只测 renderer 的数据处理；App 回归运行在 jsdom，使用内存 bridge。它们不包含真实 IPC 序列化、Host 读取/持久化、桌面布局或 GPU 时间，也不代表用户设备上的端到端耗时。本次没有更改持久化或 snapshot/notice 协议。历史仍全量传输，首次渲染很长的单会话仍会挂载全部消息；本轮没有增加虚拟列表。

## 扩展排查：流式、列表、工具、文件和启动

`node scripts/benchmark-navigation.mjs` 可复测以下独立基准。云端 Node 24.19.0，各项三次中位数，使用合成极端数据，不表示正常规模用户操作的耗时：

| 数据处理 | 条件 | 原实现 | 修复后 |
| --- | --- | ---: | ---: |
| 工具状态关联 | 一轮 2,000 次调用，6,000 个事件 | 66.33 ms | 0.76 ms |
| 项目会话分组 | 500 项目、25,000 会话 | 126.90 ms | 1.04 ms |
| 流式通知状态更新 | 25,000 历史加同步到达的 1,000 条新事件 | 519.41 ms | 2.34 ms |
| 启动恢复的终结状态扫描 | 5,000 个已完成任务、15,000 事件 | 359.08 ms | 1.33 ms |

- 工具轮次建立一次结果/执行/审批/问答索引，保留原先首条 result 优先的关联行为；搜索路径和进程附件 JSON 及参数格式化按事件引用缓存。十次父更新只解析一次同一结果。
- 项目列表一次建立所属项目和归档索引，保留原显示顺序、归档与恢复行为。
- renderer 仅将同一同步调用栈到达的通知收集到一个微任务中应用，去重及追加一次，保留事件顺序、跨会话的最后更新时间和主任务开始状态；不等待下一动画帧，不变更 Host 发出通知的时机。若事件逐个异步到达，则不会跨批次合并，改善程度取决于实际批次大小。
- 文件预览稳定来源对象，包含隐藏标签的更新不再重解析相同 Markdown，也不触发重新读取。两个标签首次解析后经历十次父更新，原实现共解析 22 次，修复后共 2 次；原实现会使新增回归失败。隐藏面板继续挂载，编辑内容不会丢失。
- 启动恢复先收集终结任务 ID，再为未结束的主任务和子任务写入失败记录。真实日志重启测试确认已结束任务不变，未结束任务只恢复一次，父任务及标题保留，不重放工具。

大历史 App 测试还覆盖切换会话时的消息隔离和有重复 ID 的流式批次顺序。现有文件、工具、审批、问答和项目交互套件验证行为兼容。

### 持久化审查与剩余瓶颈

审查确认 Agent 仍在 `await log.append(event)` 成功后才 publish；EventLog 的顺序队列、每条事件校验/追加、读取错误及崩溃恢复流程均未改变。在本云端临时目录顺序追加并读回 1,000 条合法 delta，约 173 ms（平均 0.173 ms/条）；这只描述云端文件系统，不能推断用户磁盘性能或掉电持久性。没有引入延迟写盘或提前发布。

仍保留：全量 snapshot/structuredClone/IPC，逐条异步到达通知时的历史追加复制，事件变化时重建 renderer 分组，长单会话首次全部 DOM 挂载，以及整个会话列表的 DOM 展示。当前单次流式 Markdown 仍随内容变长重解析。上述环节可能在更大规模继续占用时间；本次没有引入复杂的增量协议、虚拟列表或持久化批量策略。文件预览保留既有 100,000 字符展示上限、代码高亮 32,000 字符上限和异步请求版本保护。
